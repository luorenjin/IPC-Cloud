### 同日追加：预览**永久黑屏**（2026-10-01，用户报「预览黑屏不出图」）

- **现象**：板端 `http://172.16.1.185:8080/` 预览一直黑屏、页面显示「画面已断开，正在重连…」，但设备本身健康（`/api/v1/system/status` 正常、`/api/v1/video/params` 两个通道都 `running:true`），只有**整机重启**才恢复。
- **现场证据（真机实测）**：
  - 预览 WS（主/子码流都试）**4 秒 0 帧、0 字节**，且**连接不断**（没有报错、没有断开）；`/var/log/ipc_app.log` 干净得没有任何错误行。
  - `/proc/umap/venc`：`VpssSnd = Send + Stop` 成立，`VpssSnd`/`Stop` 一直在涨（VPSS 仍在送帧），`Send` 停在 `1000000`（**这是 MPP 计数饱和，不代表停止编码**——排查时别被它骗）；`Stop` 持续增长 = 送进来的帧**没有被编码**。

- **排查中被两个东西误导（记下来）**：
  1. `/etc/init.d/S90ipcapp restart` **不会重启应用**（见 **LEG-FW-15**）——“重启无效”其实是“重启没发生”；真正判断要看 `uptime` 与进程 pid。
  2. `Send=1000000` 是**计数器饱和**，不能用它判断编码器死活；要看 `VpssSnd` 与 `Stop` 的**增量关系**。
- **改了什么（三层，都在固件侧）**：
  1. **防御性释放（可能是根因）**：`gk_video.c` 的 `v_get_frame()` 原先在 `GetStream` 返回错误码、或**返回成功但包数为 0** 时**直接 `free` 返回，不调 `ReleaseStream`**。MPP 在这种情形下可能已经把一路 stream 划给了调用方——漏还回去就会一点点**漏干 stream buffer**，漏到一定程度 `GetStream` 永远只回 BUSY/空 → **永久黑屏**。现在这条失败路径也 `ReleaseStream`（对没拿到的 stream 是空操作），并对 `BUSY` 单独早退（不误放）。

- **尚未确证的部分（如实登记）**：原故障的**触发条件没有复现出来**，所以上面第 1 条只是最符合证据的解释（“空 stream 漏释放”）。现在两层自愈 + 带 rc 码的日志就是给下一次的：**若再黑屏，`/var/log/ipc_app.log` 里会出现 `[gk_video] 取流连续失败 … rc=0x…` 或 `[console_preview] 预览连续 8 秒无帧…`**，拿这行就能定位（rc 码决定是缓冲耗尽、通道异常还是别的）。

### 同日三追加：取消勾选后**预览仍显示旧 OSD**（2026-10-01 用户反馈）

- **现象**：在 OSD 页把「日期」「星期」**都取消勾选**后，预览画面上仍有 `2026-10-01 星期四 13:28:03` —— 看起来像“不勾也显示”。
- **先分清是哪一层**（这一步很关键，别改错地方）：
  - **设备端保存链路本身是对的**（纯 API 实测）：`POST {"time_enable":false,"time_date":false,"time_week":false}` → 回读三项都是 `false`，抓帧统计该区域**亮像素 = 0**（OSD 真的从码流里消失了）。

  | 日期 | 星期 | 上屏文字 |

### 同日四追加：OSD 中英简繁字库（2026-10-01，用户要求「通道名称需要支持字体…至少先支持中文」）

- **问题**：通道名里的汉字全渲染成 `-`（`gk_osd.c` 只手写了「星期X」九个汉字），小写字母也没有；用户要简体 / 繁体 / 英文都支持，并为将来多语言留口。

- **两个自己踩的坑**：①字库一开始写成「一个巨大的拼接字符串字面量」→ GCC 报 `-Woverlength-strings`（685440 字节 > C99 要求的 4095），改成**每字一个 72 字节的二维数组元素**；②`gk_osd.c` include 生成文件后与 `#define GK_CJK_CELL` 重复定义冲突，生成头里加 `#ifndef` 保护。
- **验收链**：①本机自检工具 `firmware/tools/osd_font_check.c`（直接 include 生成字库，用同一套解码/查表/放大逻辑渲染 PGM 看字形）——简繁英混排与「缺字只占一格」全对，宽度度量与手算一致；②交叉编译 `gk_osd.c` **零警告**；③真机把通道名设成 `门口摄像机 東門體` 与 `Door-1 门口 (A)`（含 64×64 字号）逐张截图核对：**简体、繁体、大小写字母、数字、括号**全部正确，时间 OSD 的「星期四」同屏正常。
- **代价与后续**：`ipc_app` 1.61MB → **2.26MB**（rootfs 剩 2.3MB），部署因此变脆 → 体积/多语言包见 **LEG-FW-16**，部署工具改用 TCP + 板端 tmpfs 见 **LEG-FW-17**。
- **顺带解决的现场问题**：板子没插卡也在刷 sdhci 日志、把串口提示符冲掉（`board.py` 直接超时）→ 新增 `/etc/init.d/S02mute-log`，见 **LEG-FW-18**。

### 同日五追加：OSD 叠加层**可点选 + 拖动定位**（2026-10-01，用户要求「覆盖层支持选中，拖拉覆盖层可以调整位置」）

- **背景**：这正是 **LEG-UI-18 第 ④ 条**登记过的刻意差异（实机在预览画面上直接拖 OSD，我方控制台页不做）→ 本轮补齐，LEG-UI-18 降为 **3 处差异**。
- **难点与做法**：叠加层原先**只在有未保存改动时**才画（保存后由设备自己烧 OSD，避免双份文字），所以“打开页面就想拖”时根本看不到可拖的块。解法是加一个 **`osdEdit`（鼠标在画面上）**态：pointenter 就画叠加层、pointleave 且无改动就退场，保存后一并退场。
- **交互**：每一块（time / name / char-N）带 `data-role`，按下即选中（实机同款蓝 `#578fff` 描边），拖动改屏幕位置、**松手**才换算回归一化坐标写进 S，点「保存」才下发。`osdPayload()` 本轮补上了 `time_x/time_y/name_x/name_y`（整数百分比，与 GET 回读对称）——之前只读不发，位置根本没接口能改。
- **国标模式不可拖**：时间/通道名由设备右对齐、自定义字符固定排布（设备端不用自由坐标），拖了保存也不会变——点一下给提示，不做“假拖动”。
- **两个自己踩的点**：①**事件逃不开 pointer capture**：用 `el.setPointerCapture()` 把 move/up 收到元素上（元素随重画重建，不比 window 监听容易漏）：合成事件环境下拿不到捕获就 try/catch 退回普通事件流；②**垂直方向会被夹取**：时间块本来贴底（y=90%），往下拖会立刻被“整块夹在画面内”的规则夹住，e2e 用例因此改成**往上拖**（`dy=-60`）。
- **触摸设备**：没有 hover，所以“点画面空白处”也会进入编辑态（否则叠加层永远不出现、块无从点起）。
- **验收链**：`gen_assets.py`（gzip **215934/409600 = 52%**）→ 交叉编译 `ipc_app` 2377300 → 板端部署（本轮用 `nc` + tmpfs，见 LEG-FW-17）→ 浏览器实测：hover 出现 2 块 + 2 块擦除、点选有描边、拖动 +300/+80 精确跟手、`S.osdNamePos` 写成 `[0.4462,0.222]` 且重画后位置不变（换算自洽）→ 保存后 **GET 回读 `name_x=45,name_y=22`**、截图里设备真 OSD 跑到新位置；还原后回读 `2,2` ✓ → **e2e 15/15 PASS**（新增 E15）。
- **e2e E15**（真实鼠标拖动）：先勾「日期」并**保存一次**（设备里得真有一份 OSD 才有得擦）→ 再勾「星期」制造未保存改动 → 断言叠加层 1 块可点选、≥1 块擦除 → 拖 +200/−60px（往上：往下会被夹）断言位移与选中态 → 保存后设备 `time_x` 变大、`time_y` 变小且横向换算落在 20–36% → 跑完把位置与开关还原（回出厂默认）。
- **⚠️ 断言要挂在有前提的状态上**：E15 第一版直接接着 E13（恢复出厂）跑，设备上**本来没有任何 OSD** → `savedRects()` 为空、擦除块自然是 0 个，于是“必须有擦除块”的断言把**正确行为**判成失败。修法是先用 UI 存一份真 OSD 再制造改动。

### 同日六追加：ASCII 点阵 **8×8 → 16×16**（2026-10-01，用户反馈“自适应模式下数字颗粒感很强、不够圆润”）

- **根因**：OSD 是把点阵按**整数倍**放大铺进字符格的。手写的 ASCII 表是 **8×8**，64px 档要放大 **8 倍**——一个字形像素就变成 8×8 个屏幕像素的方块，数字自然像马赛克（汉字是 24×24、只放大 3 倍，所以看着清楚）。
- **选型依据（先做对比图再动手）**：拿 Noto Sans SC 渲染同一串 `2026-10-01 17:49:12` 逐字放大对比——①**16×16 能整除全部档位**（16/32/48/64 → 1/2/3/4 倍），格宽与旧 8×8 表**完全一致**（64px 档仍是 64px），所以时间项预留宽度、右对齐、度量口径一个字都不用改；②字号要用 **22px 而不是 16px**：字体实际字高只占字号的七成，用 16px 渲染会“小一号”、四周留白过多（对比图里一目了然）；③8×16 那种“瘦高格”虽然更窄，但会改变既有度量口径，不做。
- **实现**：生成脚本新增 `--ascii-out`/`--ascii-px`（默认 22），输出 `platform/gk7205v200/gk_font_ascii.h`（95 字 × 16×16，3KB 数据，与汉字表同一字体/字重/OFL 声明）；`gk_osd.c` 删掉手写 88 行 8×8 表与 `glyph_of()`，改 `gk_ascii_lookup()`（ASCII 表按下标直查，汉字表仍二分）；`GK_GLYPH_W = GK_ASCII_CELL = 16`，`GK_OSD_BUF_W_MAX` 改写为 `(64 * 32)`（语义从“8px 格 × 8 倍”变成“64px 档 × 32 格”，值与原来一样是 2048）；自检工具 `osd_font_check.c` 里那份复制的 8×8 表也一并删掉（改为直接 include 两张生成表，以后不会再出现“改了那边忘了同步”）。
- **两个坑**：①生成器里 `"\\\\x%02X"` 多写了一层转义 → C 侧拿到的是**字面量反斜杠**（`\\x00`），数据全错；对照汉字表那行改成 `"\\x%02X"` 即可（单反斜杠）。②**自检工具的数字宽度必须先对账**：本地自检输出的文本宽度（408/248/1024/664px）与旧 8×8 表**逐字一致**，才能证明“格宽没变、不会影响已对齐的度量”这个前提成立。
- **⚠️ 前端有一份“同一口径”的副本必须一起改**：`firmware/web/js/views/camera.js` 的 `devCell()`（叠加层字符格宽）原先按 `font_px/8` 算 ASCII 格。64 档下 8 与 16 两种算法恰好都得 64，现场根本看不出来；但换成 24/32/48 档、或主码流非 1920 时自适应折算出的非常规字号，**叠加层就会与设备烧进码流的 OSD 错位**、拖拽落点也跟着偏。已同步改成 `font_px/16`（并重编译部署）。**改点阵规格时要三处一起改**：生成脚本、`gk_osd.c`、`camera.js`。
- **验收**：自检渲染图（数字有内孔、笔画 4px，且各文本宽度与旧表**逐字一致**）→ 交叉编译 `gk_osd.c` 零警告 → 板端部署（nc + tmpfs）→ 真机截图 `2026-10-01 星期四 18:57:41` 数字细腻圆润、中文与混排不受影响；`ctest` 4/4；**e2e 15/15 PASS**（含 E15 叠加层拖拽定位）。
- **未动**：汉字点阵仍是 24×24/wght600（用户未反馈问题，且 24px 是该字体的笔画平衡点：更粗会糊、更细会断）。

### 七追加：确认「OSD 已在码流里，两端抓图/录像都不用合成」（2026-10-01，用户提问）

- **结论：已支持，不需要任何合成代码**。
- **代码链路（三处核实）**：
  1. 设备端 `gk_osd.c` 的 `osd_attach_chns()` 把同一份位图挂 **`MOD_ID_VENC` 的通道 0（主）+ 1（子）**——**在编码之前**并进画面（`hal_osd.h` 的语义也是“烧进码流”）。
  2. 控制台抓图 `web/js/ui.js` 的 `snapFrom()`：只是 `canvas.drawImage(src)` + `toBlob`——**一行 OSD 绘制都没有**，拿到的就是解码后的画面像素。
  3. 控制台录像 `web/js/views/shell.js`：主码流 `video.captureStream()` / 子码流 canvas 逐帧 → 同样无合成。
- **⛔ 顺手修掉一处会误导人的旧注释**：`gk_osd.c` 文件头原先写“挂到 VPSS 的主/子两个通道上”，而实现里明确标了**本 SDK 的 RGN 挂不了 VPSS**（`MOD_ID_VPSS` 返回 `EN_ERR_NOT_SUPPORT`，因此改挂 VENC）。注释已改为与实现一致——**看代码时别被这句旧注释带偏**（“挂 VPSS 能让预览/抓图/录像都带 OSD”这个说法本身不错，但挂不了）。
- **真机实证**（不依赖截图，直接数像素）：在页面里 `canvas.drawImage(video)` 取**解码帧像素**（不含任何 DOM 叠加层），统计“接近纯白”的像素：**通道名区 302、时间区 5198**，而无 OSD 的对照区（画面中部灰墙）只有 **49**。若 OSD 是前端合成的，video 元素里根本不会有这些白像素。
- **两个容易误会的点（写下来免得重复问）**：
  - OSD 页预览上看到的那层文字是**“未保存改动的即时预览”叠加层**（保存后退场，改由设备渲染）——不是生产路径的 OSD，别拿它当“前端合成”的证据（**LC-OSD-07**）。
  - 抓图/录像的清晰度 = 码流清晰度：主码流 1920×1080 H.264 解码帧，白字边缘会有轻微压缩痕迹（属正常，非缺 OSD）。
- **附带确认**：子码流也挂了同一份位图 → 平台的实时预览（取子码流）也带 OSD；而子码流的字号不按通道缩放是另一个已登记项（**LEG-UI-19**）。

### 八追加：ASCII 点阵改**按档位预渲染多套**（2026-10-01，用户反馈“还是有点不够圆润”）

- **根因（比上一轮更本质）**：只要还是「一套点阵 + 整数倍放大」，字形就必然带台阶——16×16 在 64px 档放大 4 倍，一个字形像素 = 4×4 屏幕像素的方块。而 RGN 的 alpha 只有 **1 bit**（非透明即全透），**做不了抗锯齿**，所以唯一出路是“把点阵分辨率提到目标尺寸”。
- **做法**：ASCII 表改为**每个档位各一套**（16/32/48/64；`gk_font_ascii.h` 里 `GK_ASCII_PX[]` + 4 张表 + `gk_ascii_pick/size/lookup`），绘制时选最接近目标格宽的那套、**1:1 铺格** → 常用档（自适应 = 64px）完全无台阶。数据 89KB（95 字 ×(16²+32²+48²+64²)/8），`ipc_app` 2.37MB → **2.47MB**。
- **连带改动（渲染模型统一）**：`gk_glyph_t` 从「点阵 w×h + 整数倍 scale」改成「点阵 w×h + **目标格宽高 tw×th**」，`osd_draw` 改用**最近邻铺格**（tw==w 时自然退化成 1:1，只有非档位字号才走缩放）；ASCII / 汉字的格宽分别由 `osd_ascii_cell()` / `osd_cjk_cell()` 给出，度量、预留、右对齐三处统一走它们——**格宽口径一个字节没变**（自检宽度 408/248/1024/664px 与旧表逐字一致）。
- **⚠️ 一个坑**：`GK_ASCII_CELL` 宏在多档方案里被删了，而 `gk_osd.c` 里的 `#define GK_GLYPH_W GK_ASCII_CELL` 还在引用它 → 编译报 `undeclared`。已改为字面量 16。
- **验收**：自检渲染图（32 档就是 1:1，数字无台阶）→ 交叉编译零警告 → 板端部署 → 真机截图 `2026-10-01 19:13:43` 数字明显圆润；`ctest` 4/4；e2e 15/15。
- **汉字高分辨率（已做，见「十追加」）**：汉字要同样多档需要 9520 字 ×(24²+48²+72²)/8 ≈ **9.6MB** 放不下；**2026-10-01 改为只给常用字（GB2312 一级 3755 字）预渲染 48×48（+1.06MB）**，其余汉字回落 24×24（仍是完整覆盖，只是略粗）。
- **后续可做**：自定义字符块同样可拖（已实现，e2e 未单独覆盖）；位置目前只能靠拖，没有数值输入框（实机也没有）。

### 十追加：常用汉字 48×48 高分辨率表（2026-10-01，用户选“只给 GB2312 一级字做” ）

- **问题**：汉字只有 24×24 一套，而自适应字号（64px）的汉字格宽是 **72** → 24×24 被放大 **3 倍**，笔画比数字粗一圈（数字早在「八追加」里改成按档 1:1 了）。全量多档要 9.6MB（放不下），所以按范围拆。
- **做法**：新增 `gk_font_cjk_hi.h` = **GB2312 一级 3755 字 × 48×48**（1.06MB 数据），生成器加了 `--cjk-hi-charset`（默认 `gb2312-1`）/ `--cjk-hi-size`（默认 48）/ `--no-cjk-hi`；`gk_osd.c` 的 `gk_next_glyph()` 在**汉字格宽 ≥48** 时优先查它，未命中自动回落 24×24 全库。效果：**48 格档 1:1、自适应（72 格）档只放大 1.5 倍**。
- **关键约束（改字库时别忘）**：两张汉字表**格宽口径完全一样**（`osd_cjk_cell()` = 24 的就近整数倍），高分辨率表**只换点阵、不改格宽** → 度量/预留/右对齐不变、前端 `camera.js` 的 `devCell()` 不用改；自检工具在 32px 档的宽度与上一版**逐字一致**（408/248/1024/664px）就是证据。
- **一个易错点**：GB2312 一级字是 `0xB0A1–0xD7F9`（**不是 `0xF7`**；`0xF7` 那里是一级+二级共 6763 的末尾）。写成 `range(0xB0, 0xF8)` 会变成 6763 字 / 1.9MB（生成时曾真的这样跑过一次）。
- **附带**：48 表只盖简体常用字，**繁体字（東/門/體/國/臺…）与二级字仍回落到 24×24 放大**（自检图里能直接看出“繁”比“體”细）。要让繁体也细得再加 Big5 一级表（≈1.5MB）。
- **体积与部署**：`ipc_app` 2.47MB → **3.57MB**（md5 `a48af47f26893fec494e09883ee9a658`）；rootfs 只余 2.4MB → 覆盖写前先删了调试用的 `/usr/bin/mpp_selftest`（1.13MB，需要时重推），装完余 **2.0MB（80%）**。部署流程同前（tmpfs + nc，详见「八追加」与 `firmware/tools/README.md`）。
- **验收**：生成器 3.4s → 离线自检（四档 24/32/48/64 都渲染，32px 宽度与基线一致、48/64 档能看到常用字变细）→ 交叉编译零错误 → 板端部署 + md5 校验 → 真机截图：通道名「中间」与「星期四」笔画明显变细、与数字观感一致。

### 九追加：预览页「画面比例」**不得裁边**（2026-10-01，用户反馈“4:3 / 100% 时叠加层字体显示不全”）

- **根因（两层缩放语义打架）**：`shell.js` 的 `applyRatio()` 已按所选比例把 img/video 的**元素盒**算成「源比例的 contain 盒」，而 CSS 又给同一元素加了 `object-fit: cover` —— cover 会在元素内部**再裁一次**（首次实现在 2026-09-29 为避免“照抄实机 canvas fill 会把 16:9 拉成 4:3”而选的，当时没考虑 OSD 是烧进码流的）。
- **真机量化**（源 1920×1080，可见区 1268×785；OSD 位置从解码帧数出：通道名 x∈[2.29%,9.27%] y∈[2.13%,8.15%]，时间串 x 从 2%、y∈[90%,99.9%]）：
  | 档位 | 元素盒 | 每侧裁掉 | 实际表现 |
  |---|---|---|---|
  | 1x / 16:9 | 1268×713 | 0 | 正常 |
  | 4:3 | 1047×785 | **12.5%** | **通道名整块消失**，时间串被切成 `6-10-01 …` |
  | 100% | 1268×785 | 4.6% | 通道名只剩「间」，时间串从 `2026` 切成 `026` |
- **修法**：`.video-box[data-ratio] > img/video` 改 `object-fit: contain`（**不能改回 cover**，注释已写在 `style.css` / `shell.js` 两处）。同时消掉一个隐患：cover 会**静默丢掉视野**——4:3 档两侧合计少 25% 的画面，用户完全无从得知。
- **代价 / 与实机的刻意差异（已裁定）**：contain 不裁不拉伸，但非原始比例档会留黑边——4:3 档画面变成 1047×589（占框 62%，比 1x 小一圈）、100% 在 16:9 源下与 1x 观感相同（**铺满的观感没了**）。要“铺满”只剩两条路，都有代价：**拉伸**（4:3 纵向拉长 33%，圆形变椭圆）或**只往一侧裁**（不拉伸、OSD 也能保住，但 4:3 要丢右侧 25% 视野）。**2026-10-01 用户裁定：保持 contain**（宁可留边也不切字、不丢画面）——不属遗留，仅作决策记录。
- **验收**：交叉编译（`ipc_app` 2,467,412B，md5 `f5153dc908389ac1e4ae9c13fad45258`）→ 板端 nc+tmpfs 部署 → 浏览器实测四档 `object-fit: contain`、可见源区间均为 [0,1]（全帧完整）→ 4:3 / 100% 截图确认「中间」与完整时间串都在；已把档位恢复为 1x。
- **顺带**：会话在 `ipc_app` 重启后失效是设计如此（e2e E11），部署后重新登录即可。

### 十一追加：预览「快速切页就断连、还重连不上」→ `ipc_app` SIGSEGV（2026-10-01，用户报）

- **用户现象**：在 预览 ↔ 设置→图像 / OSD / 区域覆盖 之间**来回快速切换**，画面容易断连，而且**再也连不回来**（浏览器一直停在「画面已断开，正在重连…」）。
- **真相不是前端**：抓现场时页面报 `ws://172.16.1.185:8080/ws/v1/preview … ERR_CONNECTION_REFUSED`、板端 **`ps` 里没有 ipc_app**、`netstat` 无 8080 监听 → **进程已经死了**，所以“重连不上”是必然（S90ipcapp 只在开机拉起，不重生）。这与 **LEG-OB-03** 是同一个 bug。
- **取证链（可复用的手法）**：
  1. 用 `sh -c '<app> … ; echo EXIT=$?'` 包一层启动（`/tmp/ipc-restart-dbg.sh`），拿到 **`EXIT=139`** = SIGSEGV；
  2. `echo 1 > /proc/sys/kernel/print-fatal-signals`（该内核默认 **0**，致命信号**不打印**，这正是“无 dmesg 遗言”的原因）→ 内核打出 `Comm: **preview**`（崩在**预览推流线程**）+ 寄存器；
  3. 部署产物是 strip 过的，但 `docker run … build-app.sh` 会把**未剥离**的 `ipc_app` 留在容器 `/tmp/build-gk-arm/app/`——构建时 `cp` 一份出来（`ipc_app.debug`）即可 `addr2line`：**PC 落在 `_memcpy`**；
  4. 寄存器自洽：`dst=0xb6e980fe`（野地址、未对齐）、`src = 调用者 sp+0x20`（正好是 `ws_enqueue_frame` 里那个 `uint8_t hdr[10]`）、`lr/ip=0x10`（`memcpy` 内部把 `lr` 当移位量用）→ **崩在 `ws_ring_write` 把帧头写进环形缓冲**那一步。
  5. 复现：浏览器脚本 25ms 一次点「图像/OSD/区域覆盖/预览/设置…」循环，**旧固件 13 秒内必崩**；同时在 `netstat`/`dmesg` 上直接看到进程消失。
- **根因（`http_ws.c` 的 use-after-free）**：`console_preview` 的推流线程在 `s_mu` 保护下拿 `conn` 并调 `http_ws_send`；但**连接销毁路径（事件循环里的 `conn_close → http_ws_conn_cleanup`）从来不参与 `s_mu`**——它只短暂取一次 `ws->mu` 就把 `struct http_ws_state` **free 掉**。浏览器一断 WS（每次切页都会断一条）就可能与在途的 `http_ws_send` 重叠：生产者随后在**已释放**的 `ws` 上 `memcpy` → 写坏内存 → 整个进程 SIGSEGV。`http_ws.c` 文件头早把这条列为“已知限制 2（理论风险）”，本次真机实证。
- **修法**：`struct http_ws_state` 改**引用计数**（`refs`/`dead` + 模块级 `s_life_mu`）：
  - 连接自己 1 份；每个跨线程使用者（`http_ws_send/send_text/close/queue_used/dropped/on_text/on_close`）先 `ws_acquire()` 拿一份、用完 `ws_release()`；
  - 销毁路径只做 `ws_conn_detach()`（`c->ws = NULL`、`dead = true`、归还连接那份），**引用归零才真正 free** —— 在途发送撞上销毁时只会拿到 `HAL_EINVAL`，不可能再踩野指针；
  - 锁序固定 `s_life_mu → ws->mu`，销毁路径只持 `s_life_mu` 且不调用任何回调，无反向锁序；回调仍在 `c->ws` 置 NULL **之后**调用（保持历史语义）。
  - 同时修掉两处会**放大断连**的隐患：①`preview_thread` 的「8 秒无帧重建通路」判据把**空闲时间**也算进去——用户离开预览页 >8 秒再回来，第一次取帧稍慢就会误判为“通路坏了”而 close/open 整条视频通路（这正是 VB 池最脆弱的地方）→ 改为空闲时刷新基准；②首次 `v_open` 偶发失败（见 **LEG-FW-19**）→ 就地**重试 3 次 / 300ms**，不再把用户刚建立的预览连接踢下线。
- **验收（真机 172.16.1.185，固件 `ipc_app` 3,565,140B / md5 `07346498659f9ac55acb08f6efe5afd7`）**：`ctest` **4/4**（新增 `test_ws_lifetime_detach_vs_inflight_send`、`test_ws_lifetime_no_user_releases_immediately` 钉住引用计数契约）→ 交叉编译 → 板端部署 → **浏览器脚本 200s×2 + 150s 共 ~7,500 次切页、产生 3,389 条预览连接**（5,200 条/分钟的重连抖动）：`EXIT` 记录为空、`dmesg` 无致命信号、`重建视频通路` 计数 **0**（无上述误判），压测末尾画面仍在跑（`videoWidth=1920, readyState=4`）。对照：修前同一脚本 **13 秒**就把旧固件打成 SIGSEGV。
- **顺带实证（新增重试路径生效）**：部署后首次登录日志为 `预览连接已建立 → 预览启动失败（视频初始化）: -5，300ms 后重试（第 1 次）→（第 2 次）→ 预览已启动`，**中间没有“预览连接已断开”** → 用户侧不再出现“登录后画面先断一下再连”的现象。
- **`console_e2e.py` 结果：13/14**（`--skip-reset`，为保住用户已配的 OSD；E12 重启后自动恢复 ✓、E14 日夜时间轴 ✓）。唯一红的 **E15（OSD 叠加层拖动）与本次改动无关**：它是**用例前置状态依赖**（写死假定「通道名称」未勾选、靠勾选框本来处于未勾态来制造 dirty），本轮设备上 OSD 已配过 → 详见 **LEG-OB-04**。同轮手工复现同一序列（日期已勾 → 保存 → 勾星期）叠加层**正常画出 time+name 两块 + 2 块擦除层**，也验证了「取消日期（总开关）→ time 块消失」。**2026-10-01 因时间问题二次复跑时 E15 又红了另一种形态：`实际 ['time','name']`**（设备上「通道名称」是勾选的，叠加层本来就该画两块）——同一条写死的断言两种红法，进一步坐实“前置状态相关”而非产品缺陷。

### 十二追加：板端系统时间变成 1970-01-01 —— 不是 NTP 坏了，是「手动校时」把 NTP 关掉了（2026-10-01，用户报「板端系统时间不对」）

- **现象**：`date` → `Thu Jan 1 00:07:50 UTC 1970`（= 开机秒数）；控制台时间校对页可看到设备时间 1970；重启也不恢复。
- **排查（按序做，5 分钟定位）**：
  1. `date` / `cat /proc/uptime`：两者相等 ⇒ 墙钟**从未被校过**（本机**无 RTC**，开机即 1970）。
  2. `ps | grep ntpd`：**没有 ntpd 进程**；`/tmp/ntp_synced` 不存在 ⇒ 不是“校时失败”，是**根本没在跑**。
  3. **网络与 NTP 服务本身正常**：`ping 172.16.1.1`（2.2ms）、`ping ntp.aliyun.com`（41ms，解析到 203.107.6.88）都通；**手工**跑应用同款命令 `ntpd -p ntp.aliyun.com -S /tmp/ntp_hook.sh` → ntpd 常驻、3 秒后 `/tmp/ntp_synced` 出现、`date` 立刻变成 2026-10-01 ⇒ 链路、DNS、ntpd、hook 全好。
  4. 于是回到**配置**：`grep -oE time.ntp.enable.:[a-z]+ /etc/ipc/config.json` → **`false`**。
- **根因链**：`time.ntp.enable=false`（持久化）→ `console_ntp_read()` 返回 en=false → `console_apply_time()` 只做 `killall ntpd`（`gk_sys.c`：server 为空就直接 return）→ **ntpd 永不启动**；`console_maint.c` 的 `tick_ntp_retry()` 又因 `!en` 直接 return（所以日志里**一条 NTP 行都没有**，不像“同步失败”那样会刷告警）。写这个 false 的是**「与计算机时间同步」按钮**：`system.js` 的 `#tm-pc` 下发 `{"ntp_enable":false,"utc":…}`（语义：切到「手动校时」）。本机无 RTC ⇒ 手动校时的那份时间**重启即丢**，而 NTP 已被关掉、不会自己回来。
- **谁写的**：正是 `console_e2e.py` 的 **E7**（它就是靠切「手动校时」+ 点「与计算机同步」来验证校时，**跑完不还原**）——上一轮我用 `--skip-reset` 跑验收，E7 的 `false` 留了下来，紧接着 E12 重启 → 时间 1970。（E13 恢复出厂会清掉这个键、回到默认 true，所以“带 E13 的完整轮次”反而不会踩到；`--skip-reset` 才会。）
- **处理**：
  1. **当场恢复**：控制台 时间校对页 切回「NTP自动校时」+ 保存（等效 `PUT /api/v1/system/time {"ntp_enable":true,"ntp_server":"ntp.aliyun.com"}`）→ 重启验证：`date` 正确、ntpd 常驻、`ntp_synced` 就位，日志出现一次 `NTP 尚未同步（设备时间仍为开机计时），按缺省/已保存服务器重拉 ntpd`（重试路径按设计工作）。
  2. **防复发（已改工具）**：`console_e2e.py` 的 E7 现在**先记 `ntp_enable`/`ntp_server`，用例结束（含断言失败）在 `finally` 里一律还原**（仿 E6 的设备名做法）；跑前设备本来就是「手动校时」时会打一行 WARN 说明“这种状态重启后时间会回到 1970”。验证：完整跑一轮后 E7 明细显示 `相差 1.2s，已还原 NTP=True`，且 **E12 重启后板端时间立即恢复正确**（不再是 1970）。
- **遗留（产品层，待用户裁定，未擅自改 UI）**：本机**无 RTC**，而「手动校时」= 关 NTP = 重启丢时间。实机（TP-LINK）的同一页是这套语义。建议在 时间校对页 选中「手动校时」时加一行如实提示（例如“本机无 RTC，手动校时在设备重启后失效，建议保持 NTP 自动校时”），与 系统维护页 已有的“未校时”橙色提示同族。**按根 `AGENTS.md` 对标规则，改 UI 语义前先问用户**——未裁定前保持现状。

### 十三追加：时间校对 **默认 NTP** + **时区设置**（2026-10-01，用户要求「时间校对 默认校对方式为NTP自动校时，另外添加支持时区设置」）

- **背景**：承接「十二追加」（板端时间变 1970 = 手动校时把 NTP 关了）。本条做两件事：
  ①把「默认校时方式 = NTP自动校时」在 UI 与固件两侧都钉死；②新增**时区**设置（对标实机**无此项**，属本方新增能力，已写入 PRD `LC-SYS-07` 与 `§5.11 实现口径`）。
- **改动**（固件 C + 前端 + 模拟器 + 工具）：
  1. `core/os`：新增 `os_set_timezone(tz)`（`setenv+tzset` / `_putenv_s+_tzset`，`_WIN32` 分支只留在 core）。`app/main.c` 启动期与 `console_apply_timezone()` 都走它 ⇒ 启动、运行期两条路径**同一份实现**。
  2. `console_apply.c`：新增 `console_tz_ok()`（长度 1..63 + `CFG_CHARSET_TZ` 字符集 + **必须能解出数值偏移**）、`console_tz_offset_seconds()`（从 `console_maint.c` 上移，POSIX 符号取反，东正西负）、`console_apply_timezone()`（cfg 读值 → 缺省 `CST-8` → `os_set_timezone` → 日志）。`console_maint.c` 两处定时（重启/日夜）改为调用共享实现，符号与读数口径只剩一份。

  5. `simulator/idp/config.go`：`time.timezone` 默认值 `Asia/Shanghai` → `CST-8`（与固件 `CONSOLE_TZ_DEFAULT` 对齐；平台键表 ↔ 模拟器 ↔ 固件三处一致规则）。

- **验收（真机 172.16.1.185，`ipc_app` 3,569,236B / md5 `7621f1002176caa73ec733530338c4fa`）**：
