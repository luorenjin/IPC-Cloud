## 0. 结论先行

1. **预览页的「抓图 / 录像」走浏览器本地（存用户电脑）是正确落点，与实机一致** —— 已在本机实测落盘验证，不需要为它补设备侧能力。
2. **设备侧 TF 卡只服务「计划类」写入**（录像计划 / 抓图计划），这块我方**只有 UI、没有执行体**：保存是 `toast`，`recorder` / `snapshot` 模块未落地。
3. **存储管理页我方缺「容量管理」整块**（循环写入 ×3 + 容量配额 ×2）—— 前端 state 字段已备好（`loopRec` / `loopSnap` / `recQuota` / `snapQuota`），但页面没渲染、cfg 键也没定义。
4. 存储相关**不是一个改动，而是三条互不阻塞的链**（见 §1），应分期推进，不要捆绑。
5. **TF 卡当前不可用是硬件问题，已有独立诊断与整改清单**（《硬件基线冻结与文档排查》§8 + 2026-09-28 的 DTS/内核整改）——本专题**不重复排查**，只在卡恢复后推进写卡功能（见 §5 P0）。

## 1. 三条存储路径（语义分层）

这是本专题最重要的划分：**"存哪儿"由入口决定，不是由介质决定**。

| 路径 | 触发入口 | 落点 | 数据链 | 我方状态 |
|---|---|---|---|---|
| **A. 手动（即时）** | 预览页「抓图」「录像」按钮 | **浏览器本地**（用户电脑 Downloads） | 纯前端：canvas 抓帧 / `MediaRecorder` | ✅ **已实现，与实机一致**（2026-09-29 落盘验证：`snap_*.jpg` 185KB、`local_*.webm` ~1.1MB） |
| **B. 计划（自动）** | 存储 → 录像计划 / 抓图计划 | **设备 TF 卡** | cfg 键 → 设备执行体（recorder / snapshot 模块）→ 文件系统 | ❌ **UI 有、执行体无**：保存是 `toast`；模块未落地（LEG-FW-12） |
| **C. 平台（回看）** | 平台录像回放 / 下载 | 平台侧 `/media` | 设备推流 → ZLM → 平台录像分段 | ⚠️ 部分（多段未合并，LEG-PF-01；平台无设备磁盘字段，LEG-PF-03） |

> **关键澄清**：实机说明文字写着「如需将抓图保存在 SD 卡中，请先分配抓图容量」——那指的是**抓图计划**（路径 B），**不是**预览页的抓图按钮。两者并存不矛盾：手动抓图给"我现在要看的这张"，计划抓图给"无人值守时自动留存的这批"。

### 2.3 存储管理（我方差距最大的一页）

**卡信息表**（实机实测）：

| 序号 | 类型 | 属性 | 剩余容量/总容量 | 状态 | 操作 |
|---|---|---|---|---|---|
| 1 | 本地 | 可读写 | **56.50GB / 56.80GB** | 正常 | **格式化** |

我方表格列为 `文件系统 / 挂载点 / 已用/总容量 / 剩余 / 状态` —— 数据是真读的（`/proc/mounts` + `statvfs`），但**没有格式化按钮**。

**容量管理**（实机独有，我方整块缺失）：

| 项 | 实机值 | 语义 |
|---|---|---|
| SD 卡循环写入 | ON | 卡整体写满后是否覆盖最旧（总开关） |
| 录像循环写入 | 开启 | 录像写满后覆盖最旧录像 |
| 抓图循环写入 | 开启 | 抓图写满后覆盖最旧抓图 |
| 录像容量配额 | **90%** → 容量 51.00GB，剩余 50.70GB | 从卡总容量里划给录像的比例 |
| 抓图容量配额 | **10%** → 容量 5.80GB，剩余 5.80GB | 划给抓图；**不分配就不能存抓图** |
| 说明文字 | 「除录像和抓图外，SD 卡容量可能会被其他特色功能使用，如消息图片、视频留言等。」 | 配额之间留余量是刻意的 |
| 保存 | 落设备 | |

> 配额相加不等于 100% 也是合理的（实机 90+10=100，但说明文字暗示其它功能也占卡）——**实现时不要强制 `sum ≤ 100` 夹取**，需按实机语义定。

## 3. 我方现状盘点（按层）

### 3.1 HAL（`hal/hal_storage.h` → `platform/gk7205v200/gk_storage.c`）

| 接口 | 状态 | 说明 |
|---|---|---|
| `stat` | ✅ 真实现 | 遍历 `/proc/mounts` 找 `mmcblk`（不硬编码挂载点）→ `present/mounted/fs/mount_path`；`statvfs` 得 total/free；无卡返回 `present=false + HAL_OK`（不是错误） |
| `mount` / `umount` | ⛔ ENOTSUP | 应用层不介入（注释如此）。**但见 §5 P1：rootfs 其实没有自动挂载**——`/etc/init.d` 无挂载脚本、`11-usb-hotplug.rules` 的块设备规则是注释掉的且无 mmcblk 规则 → **卡即使枚举成功也不会进 `/proc/mounts`**，而 `stor_stat` 的 `present` 正是遍历 `/proc/mounts` 找 mmcblk → 会误报「未检测到存储卡」 |
| `format` | ⛔ ENOTSUP | **格式化按钮因此无法提供**。工具链已知（2026-09-28 板端实测）：**板上有 `mkfs.vfat`**，但内核 `/proc/filesystems` **无 exFAT** → 64GB 若是 exFAT 卡必挂不上；格式化只能出 FAT32（单文件 4GB 上限，录像分段需 <4GB） |
| `health_check` | ⛔ ENOTSUP | 表格「状态」列只能填 `OK`（来自 statvfs 成功） |
| `poll_event` | ⚠️ 恒 `EAGAIN` | 插拔事件需监听 udev netlink，**当前插卡/拔卡不会主动刷新页面** |

### 3.2 API / 能力（`modules/console/console_api.c`）

- ✅ `GET /api/v1/storage/info`：透传 HAL stat（`console_test` 有鉴权与字段断言）
- ✅ capabilities：`storage.tf`（= `caps.tf`）、`storage.record`（= `p->tf && record.enabled && mod_up("recorder")`）
- ❌ **无**格式化端点、**无**容量配额端点、**无**计划读写端点
- ⛔ `mod_up("recorder")` 恒 `UNLOADED` → `storage.record` 恒 `false`（LEG-FW-12）

### 3.3 cfg 键（`core/src/config.c`）

当前**只有 4 个**存储相关键：

```
record.enabled        BOOL
record.mode           STR   "continuous,event,schedule"
record.channel        INT   0..2
record.retention_days INT   1..365
```

**缺失**：循环写入（3）、容量配额（2）、录像计划时间表、抓图计划时间表、抓图间隔与单位、存储码流、FTP/TUMS 抓图上传开关 —— 一个都没定义，因此计划页与容量管理**无处保存**。

### 3.4 前端（`firmware/web/js/views/storage.js` + `router.js`）

- ✅ 三页结构、TF 空态门控（`tfEmpty` / `tfGate`）、`storage.tf` 能力显隐
- ✅ 存储管理表格读真数据
- ⚠️ `S` 里**已有** `loopRec / loopSnap / recQuota(100) / snapQuota(0)` —— 字段备好了但**页面从未渲染**
- ⚠️ 所有「保存」都是 `toast('已保存')`（录像计划 / 抓图计划 / 存储管理）

## 5. 分期建议

### P0 — TF 卡硬件问题（**已有诊断与整改清单，不是从头查**）

> ⚠️ 写本节前先读：[`硬件基线冻结与文档排查_GK7205V200_GC2053.md`](./硬件基线冻结与文档排查_GK7205V200_GC2053.md) **§8「插 TF 卡上电启动异常排查（2026-09-28）」** —— 那里已有 8 条硬件整改项与完整机理分析；本专题只做**定位记录与复核**，不重复论证。

**现状：TF 卡当前完全不可用**（卡没协商成功，不是「识别了没挂载」），两条独立问题叠加：

| # | 问题 | 证据 | 归因状态 |
|---|---|---|---|
| A | **插卡冷上电 → 启动卡死**（拔卡正常，4/4 必现） | 串口只输出 25 个空格即沉默，无 U-Boot/内核 → 卡点在 **ROM 启动介质选择阶段** | 已归因候选：①`UPDATE_MODE`(pin72) 上电被拉 0 → ROM 扫卡烧写；②启动源 strap 与 `SDIO0_CCLK` 共脚缺外部上下拉。**确诊手段：pin72 飞线 10kΩ 上拉复测** |
| B | **内核里卡枚举不出来**（热重启带 CD=1 正常启动，但无 `/dev/mmcblk0`） | 2026-09-28 已做软件整改（DTS 加 `cd-gpios` + `disable-wp`、内核重烧）后**热插卡仍未枚举**；2026-09-29 复核一致 | `no support for card's volts`(-22)、`error -22 whilst initialising SDIO card`、垃圾 OCR 骗驱动做 1.8V 切换、400k→100kHz 全频段失败 ⇒ **缺 47K 上拉 / CCLK 串阻·走线 / 卡槽供电(`SDIO_CARD_POWER_EN`) / 卡本身坏**（硬件整改 #4 #6 + 换卡验证）；软件侧仅剩治标的 `no-1-8-v` |

**本专题 P0 的动作**（不重复 2026-09-28 的诊断，只推进闭环）：

1. **现场**：按 §8 整改清单核对硬件（47K 上拉、CCLK 串阻、TF 座供电），**换一张已知好的卡**（先排除坏卡）；pin72 飞线确诊问题 A；
2. **若换卡+整改后仍失败**：再考虑治标内核参数 `no-1-8-v`（禁 1.8V 切换）；
3. 卡可用后做读写压测（`dd` + `md5sum` 反复校验、冷/热启动各若干次、插拔）再进 P1；
4. 结论回填本节 §6；解决则从 [`遗留问题清单.md`](../遗留问题清单.md) 删除 LEG-OB-01。

### P1（前端 + cfg 键即可闭环，不动设备执行体）

1. **容量管理块**：渲染循环写入 ×3 + 配额 ×2（state 字段已备好），新增 cfg 键并**三处对齐**，保存走 `POST /api/v1/config`。
2. **计划保存落 cfg**：录像计划 / 抓图计划的开关、周表、参数写入 cfg 键（同上三处对齐）。
   > 注意：**保存 ≠ 生效**。cfg 落盘后仍需设备执行体（P2）才会真的写卡；在 P2 完成前，UI 应如实标注（如「已保存，待设备录像能力就绪后生效」），**不要做成假开关**。
3. **自动挂载 + `present` 判定修正**（卡可用后的**前提**，否则前端永远空态）：
   - rootfs 目前**没有自动挂载**：`/etc/init.d` 无挂载脚本、`11-usb-hotplug.rules` 的块设备规则是注释掉的且无 mmcblk 规则 → 卡枚举了也进不了 `/proc/mounts`；
   - `gk_storage.c` 的 `present` 只认 `/proc/mounts` 里的 mmcblk → **应改为「块设备存在即 present」，`mounted` 单列**（前端已区分两者，见 `storage.js` 的「已插入但未挂载」提示）；
   - 挂载动作走 udev 规则（vfat/exfat），无卡时不动。
4. **格式化**：HAL `stor_format` 实现 + `POST /api/v1/storage/format`（二次确认 +「格式化会清空数据」提示）。**工具链已知**：板上有 `mkfs.vfat`，内核无 exFAT（见 D2）。
5. 抓图间隔补「秒 / 小时 / 天」档位。

### P2（设备侧执行体，工程量大）

1. **`recorder` 模块**：按 cfg 周表 + 事件触发写卡，分段（时长/大小）、循环覆盖、容量配额生效、磁盘满处理。
2. **`snapshot` 模块**：按抓图计划 + 间隔写卡，FTP/TUMS 上传。
3. 插拔事件（udev netlink）→ 推送前端刷新。
4. 平台侧磁盘字段（依赖 Flash/TF 选型冻结，见决策记录 §2.3/§2.4 第 1 项）。
