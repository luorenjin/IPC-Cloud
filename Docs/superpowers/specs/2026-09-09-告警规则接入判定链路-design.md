# 告警规则接入判定链路 + 新设备默认告警策略

| 项目 | 内容 |
|---|---|
| 日期 | 2026-09-09 |
| 关联需求 | ALM-01 布防时间模板 · ALM-02 告警规则向导 · ALM-03 设备侧事件 · ALM-04 平台侧事件 · ADD-09 接入后自动初始化 |
| 状态 | 已实施（含最终评审修复） |

---

## 1. 问题

### 1.1 告警规则与布防模板是空壳

`AlarmRule`（ALM-02）与 `AlarmTemplate`（ALM-01）目前**只有增删改查，未接入任何告警判定**。实证：

- 全仓库对 `AlarmRule` / `AlarmTemplate` 的引用，只有各自的 CRUD handler、路由，以及项目删除的级联清理；`internal/engine/` 完全没有读取。
- 开发库中 `alarm_rules` 表 **0 行**，而 `alarm_events` 已积累 **7221 条 motion 告警**。规则表为空，告警照样产生。

告警是否落库，当前只取决于 `engine.policyEnabled()` 读取的项目级设置 `alarm.policies`（ALM-05），且该设置缺省时返回 `true`（全开）。

**后果**：用户在向导里配置"仅工作日布防"，周末照样告警；配置"只关心区域入侵"，移动侦测照样刷屏。P0 功能对系统行为无约束力。

### 1.2 ADD-09 的告警部分名不副实

ADD-09 要求"接入成功后自动应用项目默认录像/告警策略"。录像部分已实现（`devsvc.ApplyDefaultRecordPlan`）。告警部分若照搬——为新通道自动创建 `AlarmRule`——在链路打通前**不产生任何实际效果**，只会插入一批影响不了系统行为的数据行，制造"已配置默认告警策略"的假象。

因此必须**先打通判定链路，再做默认策略**，顺序不可颠倒。

---

## 2. 目标与非目标

### 目标

1. 让 `AlarmRule`（通道 + 事件类型）与 `AlarmTemplate`（布防时段）真正约束设备侧告警的产生。
2. 升级过程不静默任何现有告警。
3. 新接入设备的通道自动获得默认告警规则（ADD-09 告警部分）。
4. 新建项目自动获得内置布防模板与默认告警策略。

### 非目标

- 不改动 ALM-05 `alarm.policies` 的语义与缺省全开行为。
- 不改动 ALM-02 向导前端的能力集置灰逻辑。
- 不实现 ALM-05 中标注 P1 的"外部通知"。
- 不补齐设备侧 `event.*` 能力上报（见 §6 已知限制）。

---

## 3. 设计

### 3.1 分层判定

告警事件统一经 `engine.platformEvent(ev, kind)` 落库。在现有 `policyEnabled` 之后增加一层通道规则判定，按事件来源分层：

| 层 | 事件类型 | 判定依据 |
|---|---|---|
| 平台侧（ALM-04） | `device_offline`、`node_offline`、`stream_lost`、`record_fail`、`disk_full`、`auth_fail` | 仅 `alarm.policies`，**维持现状** |
| 设备侧（ALM-03） | `motion`、`humanoid`、`intrusion`、`linecross`、`tamper`、`io` | `alarm.policies` **且** 通道规则 |
| 其余一切类型 | 上表之外的任何 kind | 按平台侧处理，仅 `alarm.policies` |

平台侧事件与通道无关（`node_offline` 甚至没有 deviceID），不应受通道规则约束。

**受通道规则约束的类型必须是白名单**，而非"非平台侧即设备侧"。接入规范 §312 列出的 IDP 事件类型还包括 `tf_error`、`tf_inserted`、`tf_removed`、`rebooted`、`bind_state`、`stream_limit`、`ota_state` 等，它们经适配器归一化后同样以 `alarm.*` 到达 `platformEvent`。若用黑名单，这些类型会因"没有匹配规则"被静默丢弃——而 ALM-02 向导根本不提供这些类型供用户配置，用户将无从恢复。故未列举的类型一律放行到 `alarm.policies` 判定。

### 3.2 通道规则判定

设备侧事件须同时满足：

1. 该 `ChannelID` 存在 `Enabled = true` 的 `AlarmRule`；
2. 规则 `Kinds` 包含该事件类型；
3. 事件时刻落在规则 `TemplateID` 指向的 `AlarmTemplate.Schedule` 布防时段内。

**边界规则**：

- 事件 `ChannelID` 为空（适配器未能归属到通道）→ **放行**。宁可多报，不可丢事件。
- 规则 `TemplateID` 为空或模板不存在 → 视为**全天候**放行。
- 同一通道存在多条规则 → 任一条满足即放行（OR 语义）。

### 3.3 布防时段求值

`AlarmTemplate.Schedule` 形如：

```json
{ "days": [1,2,3,4,5], "ranges": [["08:00","12:00"], ["14:00","18:00"]] }
```

- `days`：ISO 周内日，1=周一 … 7=周日。
- `ranges`：`HH:MM` 起止；`24:00` 表示当日结束。
- 求值须按**项目时区**（`Project.TZ`，缺省 `Asia/Shanghai`）而非服务器本地时区，否则跨时区部署布防时段会整体偏移。
- 时区解析失败时回退 `Asia/Shanghai` 并记录一次警告，不因此丢事件。

与 REC-05 录像模板共用同一 Schedule 结构，求值函数应可复用。

### 3.4 兼容策略：严格模式 + 一次性迁移

**严格模式**：无匹配规则的设备侧事件一律拦截。

直接启用会使现有部署的设备侧告警立即全部静默（当前 0 条规则）。因此配套**启动时幂等迁移**：为每个尚无任何 `AlarmRule` 的通道创建一条默认规则（全部 6 种设备侧类型 + 全天候模板），使升级后行为与升级前一致。

选择严格模式而非宽松模式（无规则=放行）的理由：宽松模式下布防模板只对"碰巧建过规则"的通道生效，同一份配置在不同通道行为不一致，长期更难解释与排障。

**迁移步骤**（顺序不可颠倒）：

1. 对每个存在通道的项目，若其没有任何内置布防模板，先调用 `SeedAlarmTemplates` 补齐——**这一步不可省略**：内置布防模板此前只为默认项目播种，其余项目一个都没有（与录像模板此前的问题相同），跳过则第 2 步无模板可引用。
2. 为每个尚无任何 `AlarmRule` 的通道创建一条规则：全部 6 种设备侧类型，`TemplateID` 指向**其所属项目**的"全天候"布防模板。

迁移创建的规则须与用户手工创建的规则完全同构（同样引用真实模板），以便在向导中正常查看与修改。

**迁移要求**：

- 幂等：以"通道无任何规则"与"项目无内置模板"为条件，重复执行不产生重复数据。
- 可观测：启动日志输出补齐模板的项目数、处理通道数与创建规则数。
- 失败不阻断启动，但须记录错误——迁移未完成时设备侧告警会被静默，日志是唯一线索。

### 3.5 新项目播种

`SeedAlarmTemplates(projectID)`，与既有 `SeedRecordTemplates` 同构，创建全天候/工作日/周末三个内置布防模板并返回"全天候"ID。

现状与录像模板此前的问题相同：内置布防模板只在 `store.Seed` 中为默认项目创建，新建项目一个都没有。`handleCreateProject` 需同时调用录像与布防两个播种函数，并写入 `alarmDefaults` 设置。

### 3.6 ADD-09 默认告警规则

`devsvc.ApplyDefaultAlarmRule(channelID, projectID)`，接口形态与 `ApplyDefaultRecordPlan` 同构，但"未配置"时的默认行为**有意不同**（最终整体评审 Critical 1 的修复）：

- 项目级设置键 `alarmDefaults` = `{ "enabled": bool, "kinds": []string, "templateId": string }`；
- **未配置视为兜底建规则，而非关闭**：读不到 `alarmDefaults` 设置时，为通道建一条兜底规则——`Kinds` 取全部 `models.DeviceSideAlarmKinds`，`TemplateID` 指向本项目内置"全天候"布防模板（项目连该模板都没有则留空，engine 把空模板判定为全天候放行）。只有设置**存在且 `enabled` 显式为 `false`** 时，才视为运营者主动选择不建规则。
- 幂等：通道已有规则则跳过；
- 校验模板归属本项目，指定的模板无效时降级为兜底模板而非放弃建规则；
- 挂载于五处通道创建点（与录像相同）：`devsvc.UpsertChannels`、`adapter/gb28181/gb.go`、`api/devices.go` 的国标确认 / ONVIF / RTSP。

**为什么与录像的"未配置=关闭"不同**：录像的"未配置=关闭"是安全默认——不建录像计划意味着不产生录像、不占存储，可逆，随时能后补，存量项目也不会因为升级而突然开始录像。告警不满足这个前提：判定链路是严格模式（§3.4，无匹配规则的设备侧事件一律拦截），"未配置=关闭"落到这里等于"未配置=永久丢事件"——被拦截的告警不会重新出现。

这条差异不是理论推演，而是被最终整体评审实锤过的真实缺陷：`store.Seed` 建了内置布防模板却不写 `alarmDefaults` 设置，`store.MigrateDefaultAlarmRules` 只在进程启动时跑一次、只能覆盖当时已存在的通道，二者叠加的后果是——空库首装后接入的第一批相机、以及升级后新增的任何通道，都会落入"未配置"区间，若这里也照搬"未配置=关闭"，其设备侧告警会被永久丢弃直到下次进程重启。修复后 `store.Seed`/`handleCreateProject` 仍会显式写入 `alarmDefaults`（`enabled: true`），但即使因为某种原因这一步被跳过或设置被误删，兜底建规则也保证通道不会陷入"无规则"的丢事件状态。

## 6. 已知限制

### 6.1 默认规则不按能力集过滤

ALM-02 要求向导"按能力集显示"事件类型。但**当前没有任何设备声明 `event.*` 能力**：

- 接入规范 §137 定义了能力矩阵（IDP ✓ / GB28181 ✓ / ONVIF ✓ / RTSP ✗），§447 要求 ONVIF 在 PullPoint 订阅成功后置位；
- 实际上 simulator 不上报该能力，服务端也没有任何写入 `event.*` 的代码；
- 数据库中四种协议通道的能力集均无 `event.*` 条目。

若默认规则与能力集取交集，结果是每条规则的 `Kinds` 都为空，迁移等于没做，设备侧告警全部静默。因此**默认规则包含全部 6 种设备侧类型**，不做能力过滤；ALM-02 向导的置灰逻辑原样保留。

代价：RTSP 等规范标注不支持事件的源也会获得规则，但这些源本就不产生设备侧事件，规则永不匹配，属无害冗余。

**后续**：待适配器按规范补齐 `event.*` 能力上报后，可将默认规则改为按能力集取交集。届时需同步处理存量规则。

### 6.2 迁移是单向的

迁移只创建规则、不删除。若判定链路需要回退，须同时删除迁移创建的规则，否则规则会继续约束告警。回退方案：将设备侧判定改回直接放行即可，无需清理数据。

### 6.3 未覆盖 ADD-09 的其余部分

ADD-09 原文还包含"拉取通道、探测 main/sub、抓封面"，本设计不涉及。

### 6.4 gb28181 多通道告警归属错位

`adapter/gb28181/gb.go:365-369` 把设备上报的告警一律归到该设备 `idx=1` 的通道，不解析告警上报本身携带的通道号。

改动前，这只影响告警列表里的显示归属（哪个通道名下看到这条记录），是纯展示问题。改动后，通道归属直接决定 `channelRuleAllows` 的判定对象，从而决定事件的生死——用户在向导里对一台国标 NVR 的通道 3 撤防，因为该设备的告警实际全部落在 `idx=1` 上，撤防操作对通道 3 的真实告警毫无作用；反过来，用户对通道 1 撤防，会连带静默该设备**全部通道**的设备侧告警，其中包含用户以为仍在布防的通道 3/4/5……

正确做法是从国标告警上报（Alarm 消息体）中解析出真实的通道/设备编码，定位到对应的 `Channel` 记录，而非硬编码 `idx=1`。这是协议适配层的改动，涉及解析国标告警消息格式、处理"上报的通道号在库里找不到对应记录"等边界情况，风险与工作量都不小，本次未做，只记为已知限制。

### 6.5 engine 包内并存两份语义相反的排班求值器

`record.go` 的 `scheduleMatches`（REC-06 录像调度）与 `alarmrule.go` 的 `scheduleActiveAt`（本次新增，ALM-02 布防判定）求值**同一个** Schedule JSON 结构（`{"days":[...],"ranges":[["HH:MM","HH:MM"],...]}`），但语义相反：

| 维度 | `scheduleMatches`（录像） | `scheduleActiveAt`（告警） |
|---|---|---|
| `days` 为空 | 全天录，且**忽略** `ranges` | 不限星期（继续看 `ranges`） |
| `ranges` 为空 | 从不录 | 全天（放行） |
| 时区 | 服务器本地时区 | 项目时区（`Project.TZ`） |

两者由同一个周×24h 网格编辑器产出的模板作为输入，用户会理所当然地认为"同一份布防/录像时段配置，语义应该一致"。当前内置模板（`days` 全选 7 天 + `ranges` 为 `["00:00","24:00"]`）恰好在两种语义下结论相同，掩盖了分歧，因此当前生产环境无可观测故障；但只要有人建出 `days` 为空（如想表达"不限星期"）或 `ranges` 为空的自定义模板，两条链路会立刻给出不同结论——同一个模板，录像判定和告警判定可能一个说"在时段内"、一个说"不在"。

设计 §3.3 曾写"与 REC-05 录像模板共用同一 Schedule 结构，求值函数应可复用"，本次实现未落实这一点——`scheduleActiveAt` 是独立新写的，未复用 `scheduleMatches`。统一两者语义会改变现有录像调度行为（`record.go` 那份求值器已在生产环境运行），属于另一个子系统的变更范围，本次不做，只在两处函数上互加了交叉引用注释，提示后来者两者不等价、修改一处需同时确认另一处。
