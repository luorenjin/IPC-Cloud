# 设备远程配置重新设计

## 背景（Context）

`platform/web/pages/devices/[id].vue` 的远程配置面板（MGR-09）自最初实现后未再系统性审查。用户反馈"目前不管是 UI/UE 都不是很满意，功能整合也不合理"，要求重新审查设计并细化。

审查产出了一份可交互 HTML 设计评审素材（本机临时文件，非仓库内容，仅用于本次评审沟通，不作为交付物）。素材里的现状复盘与重新设计方案已与本文档的结论对齐，本文档是可执行、可追溯到代码行的正式规格。

已确认的执行约束：

- **前端为主 + 只修前后端断链**：阶段划分沿用 2026-09-10 再审计计划的默认节奏——先做不动接口的前端重构（阶段 1），再做需要平台/模拟器联动的部分（阶段 2）。**本次例外**：用户已明确批准阶段 2（后端 + 模拟器白名单扩展、`reboot_required` 暴露、恢复出厂设置接口）与阶段 1 一并排期实现，不再等待"阶段 1 汇报后再决定"。
- **重启入口取舍已批准**：保留页头工具栏的"立即重启"为唯一入口；移除「设备维护」子页签里重复的"立即重启"按钮；该子页签改为承载「定时重启」计划与新增的「恢复出厂设置」。
- **区域框选（`alarm.motion.regions`）留在阶段 3，本次不实现**：需要新增画布/拖拽组件，工作量明显大于前两阶段，且固件侧该键当前无平台承载 UI，与本次"整理现状 + 补白名单"的范围不同质，单独排期。
- **i18n 已全量接入**（commit `a5bb074`，2026-09-10，ACC-09）：新增文案必须同时写入 `platform/web/locales/zh-CN/*.ts` 与 `platform/web/locales/en/*.ts`，改完后在 `platform/web` 目录跑 `python scripts/i18n-check.py` 验证键值一致性（中英键一一对应、无重复键、页面引用的 `t('xxx')` 都存在、无死键）。
- **双向契约一致性**（`AGENTS.md` §5）：新增/改动的配置键，键名/类型/取值范围必须在 `firmware/core/src/config.c`、`simulator/idp/config.go`、`platform/server/internal/api/devices.go` 三处逐字对齐；键名写错不会报错，只会静默进 `cfg.set` 的 `rejected` 列表，表现为"保存成功但没生效"的假成功。

## 一、审计结论

### 1.1 做得好、应保留的决策

- **字段声明按类型建模**（`[id].vue:159-164` `CfgField`），而不是把 `image.mirror` 这类 0/1 开关渲染成自由文本输入——避免用户写入非法值,也让合法取值一目了然。
- **`cfg.set` 的部分成功语义**：`saveCfg` 区分"全部保存成功"与"部分字段被拒绝"两种提示（`[id].vue:321-359`），对齐固件/模拟器的 `rejected[]` 拒绝列表语义（`simulator/idp/config.go:118-141`、`firmware/core/src/config.c` 的 `cfg_apply_json`），不是全有或全无的粗粒度错误。
- **数字输入不做静默钳制**（`setCfgNum`，`[id].vue:220-223`）：越界值原样显示为错误，而不是偷偷改成边界值——旧实现如果直接钳制，用户会以为改成了 300、实际下发的却是 100，这类"表面成功、值不对"的问题比拒绝更难查。
- **`supported` 白名单过滤**（`visibleCfgGroups`，`[id].vue:298-301`）：只渲染设备实际拥有的键，兼容旧后端与不同型号的字段差异。
- **定时重启计划已实现且按需懒加载**（`rebootPlan`/`loadRebootPlan`，`[id].vue:361-400`，仅在 `cfgTab === 'maintain'` 时加载）——MGR-08 的调度部分不需要重做，本次只需搬迁 UI 位置。

## 二、改进计划（按阶段顺序执行，每阶段末汇报）

### 阶段 1 · 前端重构：七段式 IA + 分组校验 + 联动（≈2.5 人日）

**目标**：把现有 22 个键位按语义重新分组为 7 个一级子页签，修掉④①②③⑤⑥这 6 个结构性问题；不改任何接口。

- **IA 重分组**：`CfgTabKey` 由 `'image'|'video'|'detect'|'record'|'maintain'` 扩为 7 个语义化 tab：`image`（画面质量）、`encode`（编码策略，取代 `video`）、`osd`（OSD 叠加，从 `detect` 中拆出）、`alarm`（移动侦测，从 `detect` 中拆出并独立命名）、`record`（录像策略）、`time`（时间与网络，容纳现有 `time.ntp.*` 并预留阶段 2 的网络字段占位）、`maintain`（设备维护）。`cfgGroups`（`[id].vue:249-295`）逐组把 `tab` 字段改到位；`cfgTabItems`（`[id].vue:182-188`）与 `platform/web/locales/{zh-CN,en}/device.ts` 的 `device.config.tab.*` 同步扩到 7 项。
- **修复④：校验与保存按分组独立**。`intBounds`/`invalidKeys` 改为按当前 `cfgTab` 过滤（或按分组建立独立的 `invalidKeys` 映射），保存按钮的禁用条件只看当前子页签的越界字段；越界提示继续就地展示，但不再跨子页签"隔空拦截"。子页签导航项在该分组存在越界值时显示红点标记（呼应审查素材里"导航项红点"的设计意图），让用户不必先切换过去才发现哪个分组有问题。
- **修复③：去重重启入口**。移除「设备维护」子页签的"立即重启"按钮（`[id].vue:739` 一带），页头工具栏按钮（`[id].vue:542`）保留为唯一入口；「设备维护」子页签保留定时重启计划（`rebootPlan` 相关，`[id].vue:361-400`，UI 位置不变），并新增本阶段的"恢复出厂设置"占位入口（危险操作、按钮态先做出来，实际请求逻辑在阶段 2 接口就位后再接线，避免前后端交叉依赖阻塞阶段 1 验收）。
- **修复⑤：预览联动**。`IMAGE_SLIDERS` 四个滑杆（`[id].vue:169-174`）改动时，若已有 `preview.src`，前端在预览层叠加实时应用亮度/对比度/饱和度/锐度的 CSS filter（`filter: brightness() contrast() saturate()`；锐度无对应原生 CSS 效果，维持"由设备编码器处理，网页预览不模拟锐化效果"的提示文案，不假装模拟）——这是纯前端叠加层，不改变 `loadPreview` 依赖的抓帧机制,依然靠手动"刷新预览"取新帧,只是滑杆改动的即时反馈不再需要等一次网络请求。镜像/翻转（`mirrorMode`）同理用 CSS `transform` 实时反映。
- **修复①②：新增编码预设档位**。`encode` 子页签在现有 7 个编码字段（`[id].vue:253-259`）之上新增"画质档位"chips（流畅/标清/高清/超清/自定义，纯前端预设，选中即批量填充 `fps`/`kbps`/`gop` 常见组合，`w`/`h`/`codec`/`rc` 不由预设代管），GOP、码率控制模式收进折叠的"高级参数"，降低单屏字段密度。分辨率字段（`video.0.main.w`/`.h`）标注"⚡ 需重启生效"徽标（依赖阶段 2 的 `reboot_required` 静态映射，阶段 1 先接入映射表但值先只覆盖这两个已知键，见下方阶段 2）。
- **修复⑥：子页签状态写入 URL**。`cfgTab` 通过 `useRoute()/useRouter()` 或 Nuxt 的 `useRouteQuery` 类工具同步到 `?tab=` query 参数，刷新/分享链接后能定位回同一子页签。
- **验证**：`cd platform/web && npm run dev`（或既有 dev 脚本）起前端，配合 `simulator -mode=idp` 起一台模拟设备，人工过一遍 7 个子页签：故意在 `encode` 填一个越界值（如 `kbps=99999`），确认只有 `encode` 子页签的保存按钮变灰、且导航项显示红点，切到其它子页签保存不受影响；确认页头"立即重启"可用、「设备维护」子页签不再有重复按钮；拖动亮度滑杆确认预览实时变化；刷新页面确认停留在同一子页签。`python scripts/i18n-check.py` 必须通过。

### 阶段 2 · 后端与模拟器联动：白名单扩展 + reboot_required 暴露 + 恢复出厂设置（≈2 人日）

**目标**：补齐固件已定义、平台侧未开放的字段（问题⑦），并新增恢复出厂设置能力（固件 `cfg_reset` 已就绪，平台侧无入口）。

- **`cfgKeys` 白名单扩展 6 个键**（`platform/server/internal/api/devices.go:497-511`）：新增 `record.channel`（int 0-2）、`time.timezone`（str）、`net.dhcp`（bool）、`net.ip`（str）、`localUser.name`（str）、`led.enable`（bool）——键名/类型/范围逐字对齐 `firmware/core/src/config.c:293,301,304-306,312` 的 `register_common_rules` 表。**`alarm.motion.regions` 不在本阶段范围内**（`CFG_T_JSON` 类型，需要区域框选 UI 才谈得上暴露，留给阶段 3）。
- **`simulator/idp/config.go` 的 `cfgRules`（28-62 行）与 `cfgDefaults()`（67-97 行）同步扩展**同 6 个键，类型/范围与上一条一致；`cfgDefaults` 补充合理出厂值（如 `time.timezone: "Asia/Shanghai"`、`net.dhcp: true`、`led.enable: true`）。
- **`reboot_required` 静态映射暴露**：固件 `reboot_required` 是规则表内部标记，从不通过 `cfg_get_json`（`firmware/core/src/config.c:452-489`）下发到线上，因此不能指望"实时读取"，只能在平台侧维护一份**静态镜像映射**（类比 `cfgKeys` 本就是固件规则表的静态镜像，不实时抓取）。在 `devices.go` 新增 `var cfgRebootRequired = map[string]bool{"video.0.main.w": true, "video.0.main.h": true, "net.dhcp": true, "net.ip": true}`（对齐 `firmware/core/src/config.c:266-267` 的 `video.%d.%s.w/h` RULE 与 `:304-305` 的 `net.dhcp`/`net.ip`，这是当前固件规则表里*仅有*的 4 个 `reboot_required=true` 键），`handleDeviceConfigGet`（`devices.go:513-541`）响应体新增 `"rebootRequired": cfgRebootRequired` 字段（或仅返回值为 true 的键名列表，视前端消费方式二选一，倾向后者以减小响应体）。前端阶段 1 遗留的徽标逻辑在此阶段接入真实数据源。
- **新增恢复出厂设置能力**（三层，从下到上）：
  - `simulator/idp/config.go` 新增 `cfgReset(keepKeys []string) `方法/函数：清空 `d.cfg` 中不在 `keepKeys` 的条目（对齐固件 `cfg_reset(keep_keys, n)` 语义，`firmware/core/src/config.c:594-614`），简化实现可直接重置为 `cfgDefaults()`。
  - `simulator/idp/device.go` 的 `onMessage` 分发（210-266 行区间）新增 `case "cfg.reset":`，与现有 `cfg.get`/`cfg.set`（250-263 行）并列，调用上一步的重置逻辑后经 `d.ack(env, code, msg, data)`（269-277 行）回包；语义上恢复出厂设置后设备应重启（对齐固件 `cfg_reset` 之后设备的预期行为与素材文案"设备将自动重启"），模拟器可在重置后触发既有的重启模拟流程（若已有可复用的重启状态迁移逻辑，复用；否则至少将设备标记为短暂离线再回线，不需要为此新增复杂状态机）。
  - `platform/server/internal/adapter/idp/media.go` 新增 `ConfigReset` 方法，紧邻现有 `ConfigGet`/`ConfigSet`（约 100-180 行区间）：
    ```go
    func (a *Adapter) ConfigReset(deviceID string) error {
        _, err := a.request(deviceID, "cfg", "cfg.reset", map[string]any{})
        return err
    }
    ```
  - `platform/server/internal/api/devices.go` 新增 `handleDeviceConfigReset`，紧邻 `handleDeviceConfigGet`/`handleDeviceConfigSet`（513-574 行区间）；请求体要求 `confirmName` 字段并校验等于设备当前名称（**镜像** `handleDeleteDevice` 的确认模式，`devices.go:226-246`：`ConfirmName string `json:"confirmName" binding:"required"``，`if d.Name != req.ConfirmName { fail(c, errs.EBadRequest.WithMsg("设备名不一致")) }`），通过后调用适配器 `ConfigReset`。非 `idp` 来源同 `handleDeviceConfigGet` 一样拒绝（`errs.EForbid`）。
  - `platform/server/internal/api/router.go` 新增路由 `POST /devices/:id/config/reset`，权限层级用 `requirePerm("config")`——与同页面其它配置读写操作（`GET/PUT /devices/:id/config`、`POST /devices/:id/reboot`）保持一致的权限门槛，不额外提升到 `"delete"`：恢复出厂设置属于"设备配置类"操作范畴（清除的是本地配置，不是平台侧的设备记录本身，与软删除设备是不同性质的破坏性操作），且已有确认名称校验作为二次确认,不需要叠加更高权限层级造成"能改配置却不能恢复出厂"的错配。
  - 前端 `[id].vue` 「设备维护」子页签接线阶段 1 留的占位按钮：点击后走 `confirmBox.ask`（**镜像** `askDeleteDevice`，`[id].vue:473-484`）弹出 `inputConfirm: devName` 的强确认弹窗，通过后调用新端点。
- **验证**：`simulator -mode=idp` 起模拟设备，前端过一遍新增 6 个字段的读取/写入（含越界值应被拒绝、体现在 `rejected` 列表）；触发一次分辨率变更确认"⚡ 需重启生效"徽标正确显示；触发一次恢复出厂设置，确认弹窗要求输入设备名、名称不符时提交按钮保持禁用/提交后报错，成功后设备配置回到出厂默认值且模拟器侧观察到设备短暂离线又恢复上线。`python scripts/i18n-check.py` 必须通过（新增确认弹窗文案、新增 6 个字段的 label/hint）。

### 风险与回滚点

1. **阶段 1 的分组校验重构**是对现有 `invalidKeys`/`intBounds` 计算逻辑的改动，如果分组归属与 `cfgTab` 的映射写错，可能出现"某字段永远不参与校验"的静默 bug（比危险的"过度拦截"更隐蔽）——每个分组切换后都要人工触发一次越界值验证，不能只测一个分组。
2. **阶段 2 的白名单扩展**必须三处（固件已是既定事实、`devices.go`、`simulator/idp/config.go`）同步，键名/类型/范围任一处不一致都会导致静默 `rejected`——每加一个键单独跑一次 `cfg.set` 验证该键能正常写入再继续下一个。
3. **恢复出厂设置**是破坏性操作，回滚点在于：新端点上线初期若确认名称校验有疏漏（如大小写/前后空格未处理导致误通过或误拒绝），应先在 `simulator` 环境反复验证多台设备名称的边界情况，再连真实固件（若有）。
4. **`net.ip`/`net.dhcp` 加入白名单**后，虽然本次只做"暴露读写"，不做前端强交互限制（阶段 2 范围只是让这两个键可读可写、可显示 `reboot_required` 徽标），但网络类字段改错会导致设备失联，若后续要素材里提到的"强确认交互，不能和其它字段共用保存按钮"，应作为阶段 2 之后的**独立跟进项**而非本次阶段 2 的隐含范围——本文档明确阶段 2 只做白名单打开与徽标，不做网络字段的专属确认流程，避免范围隐性扩大。

## 三、验证方式（贯穿）

1. 每个阶段末在 `simulator -mode=idp` 环境针对该阶段改动的字段/接口手工过一遍读取→修改→保存→重新加载确认闭环，不依赖自动化测试（`platform/CLAUDE.md` 已注明本仓库无自动化测试套件）。
2. 涉及文案改动，改完后必须在 `platform/web` 目录跑 `python scripts/i18n-check.py`，确认无未使用键、无缺失翻译、无重复键。
3. 涉及配置键新增/改动，必须在固件规则表（只读参考，本次不改固件）、`simulator/idp/config.go`、`platform/server/internal/api/devices.go` 三处比对键名/类型/范围逐字一致后再验证读写。
4. 破坏性操作（恢复出厂设置）在合入前至少验证一次"确认名称不匹配"的拒绝路径与一次"确认名称匹配"的成功路径。
