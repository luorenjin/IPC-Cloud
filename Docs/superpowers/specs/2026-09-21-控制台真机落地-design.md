## 1. 背景与目标

用户已拿到 GK7205V200 实体开发板（Linux 4.9.37 / SPI Nor 16MB / 32MB RAM / eth0 DHCP 正常 / 串口 COM6）。仓库中 `modules/console` 与 `modules/common/http_server` 的业务逻辑已完成约 4000 行并有测试覆盖，但**从未在任何真实硬件上运行过**——因为缺少三样东西：可执行程序入口、真实芯片平台的 HAL 实现、交叉编译链路。

本设计的目标是让控制台**第一次在真机上跑起来**：浏览器访问设备 IP 能登录并看到真实的设备信息。

## 2. 关键事实（已实测验证）

### 2.1 两个改变方案的发现

#### 发现一：串口无法输入，是 SDK 的 getty 配错了设备

SDK rootfs 的 `etc/inittab` 中唯一活跃的 getty 为：

```
::respawn:/sbin/getty -L ttyS000 115200 vt100 -n root -I "Auto login as root ..."
```

而板子内核命令行是 `console=ttyAMA0,115200`（PL011）。**getty 守在 `ttyS000`，终端实际连的是 `ttyAMA0`**，设备名不匹配，因此串口只有单向输出、无法输入。板子 boot log 中的 `[RCS]: /etc/init.d/S00devs` 等输出与 SDK rootfs 的 `etc/init.d/rcS` 完全吻合，可确认板子跑的就是这套 rootfs。

**两个后果**：

1. 原方案"编译 → scp 推送到 `/tmp` → 运行"整条路径依赖 shell，**全部不成立**。必须改为「打进 rootfs 镜像 → 烧录 rootfs 分区 → 开机自启」。
2. 原 spec §8 列出的 5 个开放问题（ssh 是否存在、端口占用、`/tmp` 空间、`/proc/cpuinfo` 格式、TF 卡挂载）**一个都问不出来**，必须改为从 SDK rootfs 源码静态推断，或在首次烧录后由程序自己上报。

因此本期**顺带修复 inittab**，把 getty 改到 `ttyAMA0`。修好后串口可交互，后续调试不再盲飞——这是本里程碑的高价值副产品。

#### 发现二：分区表冲突，照抄任何一方都会烧废

三份布局互不相同：

| 分区 | 板子现状（boot log 实测） | 仓库产物 `spi_partitions.xml` | PDF §2.5.2 示例 |
|---|---|---|---|
| boot | 0 – 512K | 0 – 512K | 0 – 1M |
| bootargs | 512K – 1M | 512K – 1M | （无此分区） |
| kernel | 1M – 6M（**5M**） | 1M – 5M（**4M**） | 1M – 6M |
| rootfs | **6M** – 16M（10M） | **5M** – 16M（11M） | 6M – 16M |
| rootfs 设备 | `/dev/mtdblock3` | — | `/dev/mtdblock2` |

**rootfs 起始地址差 1MB**。若按仓库产物的分区表烧录，rootfs 将写到 5M 位置，而板子 bootargs 里的 `mtdparts` 仍认为 rootfs 在 6M，挂载必然失败。PDF 的示例是第三种布局（3 分区、`mtdblock2`），PDF 自身也注明"需根据实际产品情况修改"，**不可照抄**。

**处置**：本期仅重烧 rootfs 一个分区，且**分区表必须改为对齐板子现状**（起始 6M / 长度 10M）。uboot、bootargs、kernel 一律不动。这样即使 rootfs 烧坏，U-Boot 仍完好，可经 tftp 重新烧回，**不会真变砖**。

### 2.2 其他已验证事实

后续实现不得与之矛盾：

| 事实 | 验证方式 | 影响 |
|---|---|---|
| 工具链为 **uClibc** 非 glibc（`arm-gcc6.3-linux-uclibceabi`） | docker 卷内 `find` | 动态链接跨 libc 风险高，故选静态链接 |
| `-static` + pthread + epoll + socket 可编译，产物 336KB ARM EABI5 ELF | 镜像内实测编译 | 静态链接方案可行，体积可接受 |
| **镜像内没有 cmake** | `which cmake` 返回 NO CMAKE | Dockerfile 必须补装 |
| console 只用 **17 个** HAL 成员，非全部 60 个 | grep 统计去重 | 平台实现量大幅小于初估 |
| console 每处 HAL 调用都有 `hal_has()` 加函数指针双重判空 | grep `hal_has(` 全部 20 处 | 桩化安全，不会崩 |
| console 鉴权依赖 `crypto->secure_read/write/random`（11 处） | console_auth.c:505 等 | crypto 虽在 hal.h 标"可选"，**缺了无法登录**，必须实现 |
| 全仓库零 `.html/.js/.css`，http_server 无 `/` 兜底路由 | find 加 grep 路由注册 | 前端与静态路由均需从零新增 |
| `docker/out/gk7205v200/spi_image/` 已有 uboot/uImage/rootfs.jffs2 | ls | rootfs 重打包的基线素材已就位 |
| jffs2 打包参数为 `mkfs.jffs2 -d <dir> -l -e 0x10000 -o <out>` | SDK `build/rootfs_image.mk:74-81` | `-l` 小端、64KB erase block，与板子 `Blocksize:64KB` 吻合，**参数错则 rootfs 挂不上** |
| `mkfs.jffs2` 位于 SDK `tools/utils/bin/`，docker 镜像本身无 mtd-utils | 镜像内 find 加 which | 重打包须在挂载 SDK 卷的容器内进行 |
| 烧录工具为 `tools/burning-tool/ToolPlatform-1.0.0-win32-x86_64.zip` | ls | **正好是 Windows 版**，可由用户直接运行 |
| SDK 卷 `out/gk7205v200/` 为空（构建后已清理并导出） | ls | rootfs 骨架需重新构建，或从同批次芯片目录取参考 |

### 3.3 rootfs 注入与打包

以 `docker/out/gk7205v200/spi_image/rootfs.64k.jffs2` 对应的 rootfs 目录为基线，叠加 overlay 后重新打包：

| 改动 | 内容 | 目的 |
|---|---|---|
| `etc/inittab` | `ttyS000` 改为 `ttyAMA0` | **修好串口 shell**（见 §2.1） |
| `usr/bin/ipc_app` | 交叉编译产物，strip 后置入 | 主程序 |
| `etc/ipc/SP-R1-02.json` | profile 清单 | 程序启动必需 |
| `etc/init.d/S90ipcapp` | 自启脚本，后台拉起 `ipc_app` 并重定向日志到 `/var/log` | 开机自动运行 |

打包命令固定为 `mkfs.jffs2 -d <rootfs> -l -e 0x10000 -o rootfs.64k.jffs2`（取自 SDK `build/rootfs_image.mk:74-81`，**参数不得改动**）。

**体积约束**：rootfs 分区 10MB。基线镜像 2.2MB，`ipc_app` 静态链接后预计 1-2MB，前端资源 gzip 后约 50KB，合计远低于上限，无裁剪压力。打包后须断言镜像 `< 10MB`，超出则构建失败。

**自启脚本的防御要求**：`S90ipcapp` 必须在 `ipc_app` 反复崩溃时**不阻塞开机流程**（后台启动、不 `wait`），否则程序一旦崩溃就再也进不了系统，只能重新烧录。

## 4. 组件设计

### 4.1 `app/main.c` 启动编排

唯一的非测试 `main()`。顺序严格如下，任一步失败即带错误码退出并打日志：

1. 解析参数：`--profile <path>`（必需）、`--port <n>`（默认 80）
2. `log_init()`，尽早调用，保证后续失败可见
3. 读取 profile JSON 文件到内存
4. `hal_init(profile_json)`，内部校验 `version` 与 `platform_id`
5. `cfg_init()`，profile 播种加持久化配置加载
6. `module_register(&mod_console)`
7. `module_init_all()` 然后 `module_start_all()`
8. `http_server_start(port)`
9. 安装 `SIGINT`/`SIGTERM` handler（仅设置 `volatile sig_atomic_t` 标志，不在信号上下文做实际工作）
10. 主循环等待退出标志，然后 `http_server_stop()`、`module_stop_all()`、`module_deinit_all()`、`hal_deinit()`

**设计约束**：main.c 不得包含任何业务逻辑，不得 `#include "platform/`。它只做编排。

### 4.2 `platform/gk7205v200/` 真实 HAL

装配方式与 `platform/mock/mock_platform.c` 完全一致：9 个 `extern const hal_*_ops_t`，组装成 `static const hal_ops_t`，`hal_platform_get()` 返回其地址。`platform_id` 必须为 `"gk7205v200"`，与 `profiles/SP-R1-02.json` 的 `identity.platform` 一致。

#### sys（真实实现）

| 函数 | 数据来源 |
|---|---|
| `get_info` | 芯片型号来自 `/proc/cpuinfo` 的 Hardware 字段；序列号优先读安全存储，缺失则用 eth0 MAC 派生 |
| `get_stats` | `/proc/meminfo`（MemTotal/MemAvailable）、`/proc/uptime`、`/proc/loadavg` |
| `monotonic_us` | `clock_gettime(CLOCK_MONOTONIC)` |
| `reboot` | `sync()` 后 `reboot(RB_AUTOBOOT)` |
| `factory_reset` | 删除配置目录与安全存储目录后重启 |
| `watchdog_*` | `/dev/watchdog` 存在则用，否则 `HAL_ENOTSUP` |
| `ota_*` | 本期全部 `HAL_ENOTSUP`（不碰 flash） |

#### net（真实实现，WiFi 除外）

| 函数 | 数据来源 |
|---|---|
| `get_caps` | eth 为 true；wifi 本期报 false（板子 WiFi 模块型号 TBD，见决策记录 2.3） |
| `get_status` | `getifaddrs()` 取 IP/掩码/广播；`/sys/class/net/eth0/{operstate,speed,duplex,address}` |
| `wifi_*`（scan/connect/ap_start/ap_stop 等） | 本期返回 `HAL_ENOTSUP`。console_net.c 已有判空保护，配网页会正确显示"不支持" |

#### storage（真实实现）

读 `/proc/mounts` 找 TF 卡挂载点，`statvfs()` 取容量与可用空间。**无卡时返回 `present=false` 而非错误**，这是正常状态不是故障。格式化本期 `HAL_ENOTSUP`。

#### crypto（真实实现，登录必需）

复用 mock 的文件存储思路，路径为 `/etc/ipc/sec/<key>`（jffs2 可写，目录由 overlay 预建），可经环境变量覆盖以便 x86 测试时改用临时目录：

- `secure_read/write/delete/exists`：文件读写，写入用临时文件加 rename 保证原子性，权限 `0600`
- `HAL_SEC_KEY_DEVICE_KEY` 的 read 必须返回 `HAL_ENOTSUP`（与 mock 一致，私钥不可读语义）
- `random`：读 `/dev/urandom`，失败不得退化为 `rand()`。**鉴权挑战值依赖它的不可预测性**，宁可返回错误
- `sign` 与 `get_device_cert`：本期 `HAL_ENOTSUP`（无设备证书体系）

**安全要求**：目录 `0700`，文件 `0600`。日志中禁止输出 key 对应的值。

#### video / gpio（桩）

全部函数返回 `HAL_ENOTSUP`，`get_caps` 返回全零能力。console 调用点已有判空，视频参数页会显示"不支持"，不会崩溃。

### 4.3 交叉编译链路

**toolchain file** `cmake/toolchain-gk7205v200.cmake`：设 `CMAKE_SYSTEM_NAME=Linux`、`CMAKE_SYSTEM_PROCESSOR=arm`，指定 `arm-linux-uclibceabi-gcc/ar/ranlib/strip`，`CMAKE_FIND_ROOT_PATH_MODE_PROGRAM=NEVER`、`LIBRARY/INCLUDE=ONLY`，链接标志加 `-static`。

**Dockerfile** 补装 cmake。注意 ubuntu:18.04 的 apt cmake 为 3.10，低于仓库要求的 3.16，**需下载官方二进制**。

**docker/Makefile** 新增目标：
- `fw-build`：容器内用 toolchain file 配置并构建 `ipc_app`，产物落到 `docker/out/gk7205v200/app/ipc_app`
- `fw-clean`：清理构建目录

**顶层 CMakeLists.txt** 加 `add_subdirectory(app)`。

**分层门禁不受影响**：门禁只扫 `core/*` 与 `modules/*`，`app/` 与 `platform/` 不在扫描范围。

### 4.4 前端 SPA

原生 JS 单页，无框架，无外部 CDN 依赖（设备可能无外网）。构建期由 `scripts/gen_assets.py` 转为 C 字节数组内嵌，**gzip 预压缩**后存储，响应带 `Content-Encoding: gzip`，节省 flash 且加快加载。

页面与对应端点：

| 页面 | 端点 |
|---|---|
| 登录加首次强制改密 | `POST /api/v1/auth/{challenge,login,password}` |
| 系统信息 | `GET /api/v1/system/info`、`/system/status` |
| 网络状态 | `GET /api/v1/net/status` |
| WiFi 配网 | `GET /api/v1/net/wifi/scan`、`POST /wifi/connect`（本期显示"不支持"） |
| 配置读写 | `GET` 与 `PUT /api/v1/config` |
| 存储信息 | `GET /api/v1/storage/info` |
| 重启与恢复出厂 | `POST /api/v1/system/{reboot,reset}` |

**文案一律中文**（CLAUDE.md 要求）。**能力自适应**：端点返回 501 `HAL_ENOTSUP` 时，页面显示"当前硬件不支持"而非报错。本期大量功能为桩，这是必然要求，也是 A 线设计中 501 不可退化为 404 的原因。

**http_server 静态路由**：新增最低优先级的 `/` 兜底路由，按路径查内嵌资源表；未命中返回 `index.html`（SPA 前端路由）。需处理 `ETag` 与 `If-None-Match`（资源内容哈希）以避免每次全量传输。

### 4.5 烧录流程（用户手动执行）

烧录由用户在 Windows 上用 SDK 自带 `burning-tool` 完成，本仓库负责产出镜像与操作指南。

**烧录前置**：`firmware/docs/烧录操作指南.md` 需明确写出串口号、PC 侧 IP、板端 IP 的填写方式，以及**只勾选 rootfs 一个分区**的强调提示。

**分区表**：新增 `rootfs_partitions.xml`，只含一条 rootfs 记录，`Start="6M" Length="10M"`，与板子现状一致。**不得复用仓库中原有的 `spi_partitions.xml`**（它的 rootfs 起始为 5M，见 §2.1 发现二）。

**回退路径**：只烧 rootfs 时 U-Boot 保持完好。若新 rootfs 无法启动，可在 U-Boot 命令行（开机按任意键即可输入，此时尚未进 Linux，不受 getty 问题影响）用 tftp 把原 `rootfs.64k.jffs2` 烧回 6M 位置恢复。此回退步骤须一并写入操作指南。

**验证顺序**（写入指南，供用户逐步确认）：

1. 烧录后重启，串口应能看到 `[RCS]` 启动日志
2. 串口**应能输入命令**（inittab 修复生效的标志）
3. `ps` 应能看到 `ipc_app` 进程
4. 浏览器访问板子 IP，应出现登录页

## 5. 错误处理

- **启动失败**：main.c 每步失败都打印中文错误与 `hal_strerror()`，返回非零退出码，串口可见。
- **HAL 桩返回 501**：前端显示"不支持"，不弹错误提示。
- **安全存储不可用**：`crypto_store_available()` 为 false 时 console 鉴权会拒绝登录，这是正确行为（凭据无处存放）。启动时应检测并在日志中明确告警。
- **端口被占**：`http_server_start` 失败应明确提示"端口 N 被占用"，便于换端口重试。

## 6. 测试策略

| 层次 | 方式 | 通过标准 |
|---|---|---|
| 既有测试不回归 | x86 mock 构建加 `ctest` | `fail` 必须为 0（含 hal_conformance / core_test / console_test / http_server_test） |
| 新平台单元测试 | `tests/platform_gk_test`，x86 上测可测部分（/proc 解析、安全存储原子写、路径处理） | 全过 |
| 交叉编译产物 | `file` 确认 ARM EABI5 静态链接；strip 后记录体积 | 产出有效 ELF |
| rootfs 镜像 | 打包后断言体积 `< 10MB`；校验 overlay 四项均已注入 | 镜像可烧录 |
| 烧录后开机 | 串口观察启动日志 | 出现 `[RCS]` 且无 kernel panic |
| **串口 shell 修复** | 串口敲 `ls` 回车 | **有回显与输出**（本期关键副产品） |
| 真机冒烟 | 串口执行 `ps` 与 `curl 127.0.0.1:8080/api/v1/system/info` | 进程在，返回真实芯片、内存、运行时长 |
| 真机端到端 | 浏览器完整走登录、改密、看系统信息、看网络状态、改配置、重启 | 全流程无错误 |

**hal_conformance 说明**：该测试校验必选模块函数存在性。gk7205v200 的桩函数**存在但返回 `HAL_ENOTSUP`**，符合 HAL 契约（`hal/hal.h` 明确"可选模块不支持时置 NULL"，必选模块的单个函数返回 `HAL_ENOTSUP` 是允许的）。若一致性测试对此有更严格断言，**以测试为准调整实现，不得修改测试来迁就实现**。

## 7. 安全考量

- 静态链接体积增大但消除运行时库劫持面。
- 安全存储文件权限 `0600`、目录 `0700`；`secure_write` 用临时文件加 rename 原子替换。
- `random` 必须来自 `/dev/urandom`，绝不退化为 `rand()`。
- 日志脱敏沿用 `log_mask()`，禁止输出口令、验证码、会话令牌（A 线规则 R8）。
- **本期为 HTTP 明文**，A 线已用挑战-响应抑制口令明文传输；仅限可信内网联调使用。

## 8. 开放问题

**前提变更**：串口无法输入（见 §2.1 发现一），原计划"Task 1 串口采集板子信息"**已不可行**。这些问题改为从 SDK rootfs 源码静态推断，并在首次烧录后由已修好的 shell 复核。

| 问题 | 影响 | 本期处置 |
|---|---|---|
| 80 端口是否被占用 | 可能需改端口 | **默认用 8080 启动**，避开与原厂程序及 ONVIF（profile 中 onvif.port 为 80）冲突；首次烧录后经串口 `netstat -ltn` 复核，确认空闲再考虑改回 80 |
| `/proc/cpuinfo` 的确切字段格式 | `get_info` 解析逻辑 | 按 ARM 通用格式解析 `Hardware` 字段；**解析失败时回退为 profile 中的 `identity.platform`**，不得因解析失败而启动失败 |
| TF 卡挂载点路径 | storage 候选路径 | 遍历 `/proc/mounts` 匹配 `mmcblk*` 设备而非硬编码挂载点；无匹配则 `present=false` |
| rootfs 是否已含所需目录（`/var/log`、`/etc/ipc`） | 自启脚本与安全存储落地 | overlay 中显式创建；`S90ipcapp` 启动前 `mkdir -p` |
| jffs2 为只读还是可写 | 安全存储能否持久化 | 板子 bootargs 含 `rw`，jffs2 可写。**但 flash 写入有寿命限制**，配置与凭据写入须避免高频 |

**通用原则**：本期所有不确定项一律选择「失败不阻断启动」的处置。程序必须在任何一项探测失败时仍能启动并提供 HTTP 服务——否则一旦启动失败，在串口修好之前将无从诊断。
