## 二、计划外发现并修复的缺陷（5 项）

这些**不在**原审计问题表中，是执行过程中实测发现的。按严重度排序：

### 1. RTSP 诊断成功即 panic（服务进程崩溃）

`adapter/rtsp/rtsp.go` 用 `map[bool]string{true:"", false: err.Error()}[ok]` 二选一取值。
Go 的 map 字面量**两个 value 都会先求值**，因此探测成功（`err == nil`）时
`err.Error()` 触发空指针，击穿 HTTP handler 导致整个服务进程崩溃。

- 独立复现确认："旧写法确实 panic: invalid memory address or nil pointer dereference"
- 修复后对**在线的** RTSP 设备实跑诊断：`{"ok":true,"cost":1,"msg":""}`，进程存活，全程 0 panic
- 已补回归测试（`rtsp_test.go`，2 个用例）

### 2. wshub 写泵超时顺序错误（连接开着但只收得到第一条消息）

`SetWriteDeadline` 写在 `WriteJSON` **之后**，等于把上一条消息的截止时间留给下一条。
首条之后截止时间早已过期，后续每次写都失败并静默退出写泵。

此 bug 长期被"每次路由切换都重建连接"掩盖——反正每次都是新连接，第一条总能送达；
阶段 2 改成单连接后才暴露。同时启用了原本创建却从未使用的 25s ping 心跳。

- 修复后实测：连续两次触发事件，消息数 2 → 4 → 6，页面两次都自动刷新

### 3. `/tasks` 跨项目越权（租户隔离漏洞）

路由缺 `requireProjectID()`，`handleListTasks` 也不按项目过滤，
任何登录用户可读取**其他租户**的任务记录（含录像文件 URL）。

- 已补中间件 + 按 `result.projectId` 过滤；实测无项目头时返回 400

### 4. 存储概览表名写错（34.7GB 录像报 0）

`handleStorageOverview` 硬编码表名 `record_indexes`，而 GORM 实际建表为
`record_indices`（英文复数不规则变化），JOIN 静默失败。

- 查库确认：2961 段共 37185245845 字节，接口却返回 `usedBytes: 0`
- 改为按 `NamingStrategy` 推导表名后，返回 2963 段 / 34.7GB / 6%，与库中一致

### 5. 调度器索引错位（最后一个媒体节点永不参与调度）

`for i := range nodes[1:]` 配 `nodes[i]`：i 从 0 起而取的是原切片，既错位又漏掉末位节点。

- 抽出纯函数 `pickLeastLoaded` 并补 5 个测试，其中一个专门把最优节点放在末位

### 另：阶段 2 自身引入、阶段 5 修复的一处

阶段 2 把首页 `dash` 改名 `dashboard` 时漏了模板里 3 处 `dash?.`。
可选链不报错，**设备总数与在线数一直静默渲染为 0**，阶段 5 重做首页时修复。
